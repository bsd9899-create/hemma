# معمارية الخادم — هل Supabase وحدها تكفي؟

سؤالك بالضبط: هل نحتاج خادمًا منفصلًا، أم Supabase وحدها تكفي؟
الإجابة القصيرة: **تكفي، ولا يوجد سبب حقيقي لإضافة خادم الآن.**
الإجابة الطويلة أدناه، مع الحالة الوحيدة التي تُغيّر هذا الحكم.

---

## 1. ما يحتاجه التطبيق فعليًا من جهة الخادم

| الحاجة | من ينفّذها اليوم | تحتاج خادمًا منفصلًا؟ |
|---|---|---|
| تسجيل الدخول (Apple / Google) | Supabase Auth | لا |
| قراءة وكتابة بيانات المستخدم | Postgres + RLS | لا |
| عزل بيانات المستخدمين عن بعضهم | RLS + GRANT | لا |
| تحديث الفرق لحظيًا | Supabase Realtime | لا |
| استقبال webhook من RevenueCat | Edge Function | لا |
| حذف الحساب (يتطلب صلاحية admin) | Edge Function | لا |
| مهام مجدولة (تجميع يومي، تصفير السلاسل) | pg_cron داخل Postgres | لا |
| إشعارات Push | Edge Function → Expo Push API | لا |
| تحليل صورة طعام بالذكاء الاصطناعي | Edge Function (المفتاح السري فيها) | لا — بشروط، انظر §4 |

كل بند هنا مغطّى. لا يوجد بند واحد يفشل بلا خادم منفصل.

---

## 2. لماذا Edge Functions تكفي مكان خادم دائم

الحاجة الحقيقية الوحيدة لكود يعمل "على الخادم" في تطبيق كهذا هي
**حيازة سرّ لا يجوز أن ينزل إلى الجهاز**: مفتاح service role، سرّ
webhook، مفتاح مزوّد ذكاء اصطناعي. Edge Function تفعل هذا بالضبط:
كودها لا يصل للعميل، وأسرارها في `supabase secrets` لا في الحزمة.

ما تقدّمه إضافةً على خادم عادي:

- **لا خادم يُدار**: لا تحديث نظام، لا شهادات TLS، لا مراقبة uptime.
- **التكلفة صفر عند الخمول**: خادم دائم يُحاسَب وهو نائم؛ الدالة لا.
- **سطح هجوم أصغر**: لا منفذ SSH، لا خدمة مكشوفة دائمًا.
- **مكان واحد للأسرار**: إضافة خادم = مخزن أسرار ثانٍ يجب مزامنته
  ومراجعته، وهذا بحد ذاته مصدر تسريبات.

---

## 3. الثمن الحقيقي لإضافة خادم منفصل

ليس الثمن ماليًا فقط:

1. **مفتاح service role في مكان إضافي.** هذا المفتاح يتجاوز RLS
   بالكامل. كل موضع جديد يوجد فيه هو موضع جديد قد يتسرّب منه، ونسخة
   واحدة مسرّبة = قراءة وكتابة كل بيانات كل المستخدمين.
2. **مصدر حقيقة ثانٍ للصلاحيات.** اليوم قاعدة البيانات هي الحَكَم
   الوحيد. خادم يتحدث بـ service role يصبح حَكَمًا موازيًا، وأي خطأ
   في `if` داخله يتجاوز RLS كلها بصمت.
3. **تعقيد نشر دائم**: بيئة، مراقبة، سجلات، ترقيات أمنية.

إضافة خادم بلا حاجة تقنية مثبتة هي **زيادة في المخاطر الأمنية**،
لا زيادة في القدرة.

---

## 4. متى يتغيّر هذا الحكم؟

هذه هي الحدود الفعلية لـ Edge Functions التي تُلزمنا بخادم لو تجاوزناها:

| الحد | القيمة التقريبية | الميزة التي قد تصطدم به |
|---|---|---|
| زمن التنفيذ | ~150 ثانية للطلب | تحليل دفعة صور، تقارير ثقيلة |
| لا طوابير مهام مدمجة | — | إعادة محاولة موثوقة لمهام فاشلة |
| ذاكرة محدودة | — | معالجة صور كبيرة قبل الإرسال للنموذج |

**الخلاصة العملية**: تحليل صورة طعام واحدة عبر Edge Function يبقى
ضمن الحدود بسهولة (رفع الصورة إلى Supabase Storage، ثم استدعاء
النموذج بمفتاح مخزَّن في الدالة). ما يخرج عن الحدود هو المعالجة
الدُفعية أو الطوابير ذات إعادة المحاولة — ولا وجود لأيٍّ منهما في
خطة المنتج الحالية.

**القرار: لا خادم منفصل. يُعاد النظر فقط عند ظهور حاجة من الجدول أعلاه
فعليًا، لا احتياطًا.**

## 5. لوحة الإدارة (Admin Dashboard)

### الخيار المرفوض

لوحة ويب منفصلة تحمل مفتاح service role. هذا أسوأ تصميم ممكن: تطبيق
كامل مكشوف على الإنترنت يحمل مفتاحًا يتجاوز كل سياسات الأمان. أي ثغرة
فيه (XSS، تبعية مخترقة، جلسة مسروقة) = قاعدة البيانات كلها.

### التصميم المعتمد

**الصلاحية في قاعدة البيانات، لا في الواجهة.** راجع
`supabase/migrations/20260906000002_admin_role.sql`:

- عمود `is_admin` على `profiles`، افتراضيًا `false`، **لا يستطيع
  المستخدم تعديله** (سياسة التحديث تمنع تغيير هذا العمود تحديدًا).
- دالة `public.is_admin()` بـ SECURITY DEFINER.
- **Views تجميعية فقط** يقرأها الأدمن: أعداد ومتوسطات. لا وزن شخص،
  لا وجباته، لا نومه. الأدمن يرى صحة المنتج، لا صحة الناس.
- الترقية إلى أدمن تتم يدويًا من SQL Editor فقط، ولا مسار لها من أي
  واجهة — فلا يوجد طلب HTTP يمكن أن يمنح أحدًا صلاحية.

النتيجة: حتى لو انتحل مهاجم واجهة الأدمن كاملة، قاعدة البيانات ترفض
طلباته لأنه ليس أدمن فيها. الواجهة تُخفي الأزرار؛ **الحماية في الصفّ
لا في الزر**.

### أين تعيش الواجهة؟

اليوم: **Supabase Studio هو لوحة الإدارة**، مع الـ views الجاهزة أعلاه.
بناء واجهة إدارة مخصّصة قبل وجود مستخدمين حقيقيين هو بناء لمشكلة لم
تظهر. الأساس الأمني جاهز الآن، فمتى احتجت واجهة (داخل التطبيق أو على
الويب) تُبنى فوق نفس الـ views بلا أي مفتاح service role.

## 6. المعمارية النهائية

```
        تطبيق هِمّة (iOS)
                │  anon key فقط — لا سرّ فيه
                ▼
    ┌───────────────────────────────┐
    │          Supabase             │
    │                               │
    │  Auth ── Apple / Google       │
    │                               │
    │  Postgres                     │
    │    └ RLS + GRANT ← الحَكَم     │
    │        الوحيد في الصلاحيات     │
    │                               │
    │  Realtime ── الفرق             │
    │                               │
    │  Edge Functions (تحمل الأسرار) │
    │    ├ revenuecat-webhook        │
    │    ├ delete-account            │
    │    └ (لاحقًا) تحليل الطعام      │
    └───────────────────────────────┘
         ▲                    ▲
         │                    │
    RevenueCat          himmah.online
    (webhook)          (موقع ثابت، بلا خادم)
```

نقطة واحدة تستحق الانتباه: **anon key ليس سرًّا.** الحماية كلها في RLS.
هذا مقصود ومكتوب صراحةً في `src/data/supabase.ts` — من يظن أن إخفاء
anon key حماية سيبني تطبيقًا مكشوفًا اليوم الذي يُستخرج فيه المفتاح
من الحزمة، وهو يوم يأتي دائمًا.
